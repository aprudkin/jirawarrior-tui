# Issue tracker

Трекер проекта — GitHub Issues:
https://github.com/aprudkin/jirawarrior-tui/issues.
Во всех вызовах CLI задавай `--repo github.com/aprudkin/jirawarrior-tui`;
для API — `gh api --hostname github.com` с явным endpoint этого репозитория.
Это трекер разработки приложения, не рабочая Jira пользователя.

PR не являются входом triage по умолчанию. Явно порученный разбор PR
остаётся возможен; автоматическое обнаружение чужих PR не настроено.

## Найти или создать задачу

Для самостоятельного содержательного результата найди соответствующую issue
до реализации. Проверяй открытые и закрытые задачи по цели, симптомам
и синонимам; общая тема ещё не доказывает дубликат.

```sh
gh issue list --repo github.com/aprudkin/jirawarrior-tui --state all --limit 100 --json number,title,state,labels,assignees
```

Это ограниченная выборка: при большем backlog используй смысловой `--search`
и дополнительные страницы через API. Прочитай body и относящиеся comments
кандидатов. Закрытый результат переиспользуй; повторный дефект или новая работа
после закрытия требуют новой связанной issue, не автоматического переоткрытия.

Если подходящей задачи нет, создай её через `gh issue create` с явным repo,
`--title` и `--body-file`: цель, контекст, результат, критерии приёмки,
ограничения. Проверь созданную задачу и сообщи ссылку. Регистрация сама по себе
не разрешает реализацию. Публикуй только безопасный контекст без приватных
данных Jira, секретов и сырых transcripts.

## Принятие и жизненный цикл

Перед каждым переходом перечитай состояние, метки, исполнителей и нужные
комментарии. Для ручных команд ниже сначала выбери проверенный номер issue:

```sh
printf 'Номер issue: ' && IFS= read -r issue && test "$issue" -gt 0
```

Чтение задачи:

```sh
gh issue view "$issue" --repo github.com/aprudkin/jirawarrior-tui --json number,title,state,body,comments,labels,assignees,url
```

- **Принятие / возобновление:** до реализации добавь `in-progress`.
  Если исполнителей нет, назначь себя через `--add-assignee @me`; существующие
  назначения сохраняй. Другой исполнитель или уже имеющаяся `in-progress`
  исключают автоматический захват: нужна подтверждённая связь с текущим
  поручением/хэндофом либо явная передача. Один login не доказывает одну сессию.
  При неоднозначности уточни принадлежность. Чтение, обсуждение, создание
  задачи и стартовая сводка не означают принятия.

```sh
gh issue edit "$issue" --repo github.com/aprudkin/jirawarrior-tui --add-label in-progress
```

- **Ожидание:** инструмент, субагент, побочный вопрос и временный блокер
  сохраняют `in-progress`.
- **Остановка / откладывание / смена работы:** оставь issue открытой,
  запиши причину и остаток комментарием через `gh issue comment` с явным repo
  и `--body-file`, затем точечно сними метку.

```sh
gh issue edit "$issue" --repo github.com/aprudkin/jirawarrior-tui --remove-label in-progress
```

- **Завершение всей цели:** сначала зафиксируй результат, фактические проверки,
  пропуски/ограничения и ссылку на commit, если он есть. Затем закрой issue
  и сними `in-progress`; завершение одного шага не завершает всю задачу.

```sh
gh issue close "$issue" --repo github.com/aprudkin/jirawarrior-tui --reason completed && gh issue edit "$issue" --repo github.com/aprudkin/jirawarrior-tui --remove-label in-progress
```

После любой записи перечитай фактическое состояние. Уже достигнутый статус —
no-op, не повод для повторного комментария/записи. Сохраняй прочие метки
и исполнителей; применяй точечные add/remove, а не замену всего списка.
При неизвестном исходе сначала читай; при ошибке сообщи точный этап, не выдавай
его за успех и не подменяй отказ изменения метки закрытием задачи.
Чтение и запись не дают атомарного захвата: конфликт требует выяснения владельца.

`in-progress` — независимый от triage статус исполнения
(стандарт при создании: `1D76DB`,
`Issue accepted for implementation; work is ongoing`).
Уже существующую метку сохраняй без изменения цвета/описания.
Локальный `current_ticket` не синхронизирует GitHub; статусы обновляет агент.
При недоступном GitHub сообщи ограничение и продолжай независимые разрешённые
части работы; это не доказательство отсутствия задач или успешной записи.
